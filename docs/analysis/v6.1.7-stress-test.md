# v6.1.7 — 极限压力测试 (100 订单 × 全产品)

## 目标
验证当前 v6.1.5 能否承受 100 个客户同时下单全部虚拟产品的尺度

## 测试场景设置
- 100 个订单，每个订单十五个虚拟产品
- 共计: 1500 条产品条目需要分配 Key
- PHP max_execution_time = 30s
- memory_limit = 128M

## 发现的 12 个问题

### P0 — 必须立即修复

**问题 1: wp_cache 不跨请求持久 (P0)**
ks_order_lock 使用 wp_cache 存储锁，但 WordPress 默认对象缓存只在当前 HTTP 请求内有效
两个管理员可以同时操作同一个订单——锁完全失效
修复: 用 set_transient 替代 wp_cache

**问题 2: CSV 模式不发送邮件 (P0)**
CSV 导入只保存 Key，不触发邮件发送。
管理员用 CSV 批量处理后——Key 已保存但客户收不到邮件
且订单不会被标记为 Completed
修复: CSV 处理后发送邮件

**问题 3: TOCTOU 竞争条件 (P0)**
先 check 后 lock，两个并发请求都可以通过 check
修复: 单一原子操作锁

### P1 — 高优先级

**问题 4: CSV 单请求处理超时 (P1)**
1500 行 × ~50ms = ~75s 超过 30s 限制
PHP 杀死进程后部分 Key 已保存，部分丢失
没有断点续传机制
修复: 分片处理 + 进度显示

**问题 5: Key 去重 SQL 查询性能 (P1)**
LIKE 查询在 postmeta 大表上随数据量增长变慢
1500 次查询每次扫描整个 postmeta 表
修复: 精确匹配或添加索引

### P2 — 中优先级

**问题 6: 无邮件重试机制 (P2)**
Brevo 和 wp_mail 都失败时 Key 已保存但客户收不到邮件
修复: 添加失败队列 + Resend 功能

**问题 7: Dashboard 每页加载查询 100 个订单 (P2)**
每次 WP Admin 页面加载都触发数据库查询
修复: 缓存订单数量

**问题 8: CSV 文件类型未验证 (P2)**
仅依赖浏览器端 accept=.csv
修复: 服务端 MIME 类型验证

## v6.1.7 复修内容

### 修复 1: wp_cache → set_transient (持久锁)
原先: wp_cache 只在当前 HTTP 请求内有效，两个管理员可同时操作同一订单
现在: set_transient 存储在数据库，跨请求有效

### 修复 2: TOCTOU 竞争条件
原先: 先 check 后 lock，两个并发请求都可以通过 check
现在: 直接使用 set_transient 的原子操作锁，失败则重定向

### 修复 3: CSV 模式邮件发送 + 订单完成
原先: CSV 导入只保存 Key，不发邮件、不更新订单状态
现在: 添加 ksc() 函数，每次保存后检查是否完成，发送邮件 + 标记 completed

- Key dedup LIKE 查询性能
- Dashboard 查询优化
